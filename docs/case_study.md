## 1. 문제 (왜 시작했나)

독거 고령자는 혼자 지내는 시간이 길어 돌봄 공백이 생기기 쉽다. 인지기능 저하처럼 스스로도 알아차리기 어려운 변화는 본인도, 가족도 조기에 판별하기 어렵고, 자녀는 생업 때문에 매일 방문·통화하기 어렵다. 그 결과 문제가 뚜렷해진 뒤에야 뒤늦게 발견되는 경우가 많다.

Callog(콜록)은 어르신이 매일 짧은 안부 체크(지병 맞춤 질문 + 음성 한마디)를 남기면, AI가 이상 신호를 조기에 감지해 보호자에게 위험도에 따라 단계적으로 알리는 조기 감지 서비스다. 다만 **"진단"은 하지 않는다** — 법적·신뢰 리스크를 피하기 위해 AI는 "확인이 필요한 변화"만 짚어주는 역할에 머문다.

## 2. 과정 (어떻게 만들었나)

| 단계 | 내용 |
|---|---|
| 기획 코칭 (3~4강) | MVP 범위표·화면 설계로 필수/나중/버림을 구분. "AI 안색·표정 진단"은 개인정보·신뢰성 문제로 이 단계에서 명시적으로 버렸다 |
| 첫 배포 (5강) | 정적 데모(`demo/index_0812.html`)를 Vercel에 배포. 빌드 과정 없이 정적 파일만 올라가 있어 `/` 경로에 아무것도 뜨지 않는 문제를 `vercel.json` 리라이트로 해결 |
| 리브랜딩 | 서비스명을 "장수기록" → 최종적으로 **"Callog(콜록)"**(Call + Log)으로 확정, 호칭도 "인생 선배/인생 후배" 등 여러 안을 거쳐 최종적으로 "어르신/보호자"로 되돌렸다 |
| 실제 앱 구축 | React + Vite + Supabase로 13개 화면 전체를 실제로 구현. 정적 데모가 아니라 회원가입·데이터 저장·권한 통제가 되는 앱으로 전환 |
| 고도화 (6강) | Gemini 연동, 이메일 인증 방식, 위험도 가중치 등 우선순위를 정해 하나씩 처리 |

**같은 이름의 기능이 하루 만에 두 번 바뀐 것**이 이 프로젝트의 특징이다 — 8/18 하루 동안 "장수기록" 리브랜딩 회의, "Callog" 재명명, 13개 화면 스캐폴딩이 순서대로 일어났다. 기획 문서가 실제 코드 진행 속도를 따라가지 못해서, PRD를 5차까지 개정하며 "계획 대비 실제" 간극을 계속 좁혀야 했다.

## 3. 기술적 의사결정과 디버깅 — 계획대로 되지 않았던 것들

포트폴리오에서 가장 보여주고 싶은 부분은 "처음 계획이 실제로 부딪힌 문제와, 그것을 어떻게 확인하고 고쳤는가"다.

### 3.1 접근 통제 — Postgres RLS 설계

가족 계정(보호자)과 어르신 프로필은 1:N 관계이고, 어르신은 앱 설치 없이 초대 링크로만 접속한다(익명 세션). 이 두 종류의 사용자가 서로의 데이터를 볼 수 없어야 하므로, 모든 핵심 테이블에 Row Level Security를 적용했다.

```sql
create function owns_elder(p_elder uuid) returns boolean
language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from elder_profile e
    where e.id = p_elder and e.family_account_id = auth.uid()
  );
$$;
```

화면 단위로도 `ElderRoute`/`GuardianRoute` 라우트 가드를 둬서, 어르신의 익명 세션으로는 보호자 화면에, 그 반대로는 접근할 수 없게 이중으로 막았다.

### 3.2 보안 취약점을 실제로 찾아서 고친 경험

Supabase의 보안 어드바이저(`get_advisors`)가 `SECURITY DEFINER` 함수들의 `search_path`가 고정되어 있지 않다고 지적했다. `search_path`가 없는 `SECURITY DEFINER` 함수는 호출자가 세션의 `search_path`를 조작해 의도하지 않은 스키마의 동명 함수/테이블을 참조하게 만들 수 있는 잘 알려진 Postgres 취약점이다. 지적을 받은 뒤 모든 관련 함수에 `set search_path = public`을 명시적으로 추가해 재검증했다.

### 3.3 "조용히 실패하는" 버그 두 건

- **Gemini 모델 폐기**: 사용하던 `gemini-2.0-flash` 모델이 Google 쪽에서 폐기되면서 모든 음성 분석·질문 생성 호출이 404로 실패하고 있었는데, 실패를 잡아 기록하는 코드가 없어서 한동안 "정상 동작처럼 보이지만 실제로는 전부 fallback"인 상태로 방치돼 있었다. `gemini-3.6-flash`로 모델명을 갱신하고, 실패 시 `analysis_status`를 명시적으로 기록하도록 함께 고쳤다.
- **JSON 마크다운 래핑**: 모델을 갱신한 뒤에도 Gemini가 JSON 응답을 \`\`\`json 코드블록으로 감싸 보내는 바람에 `JSON.parse`가 계속 실패했다. 원인은 `generationConfig.responseMimeType` 설정 누락이었고, 코드블록을 방어적으로 벗겨내는 처리를 추가해 해결했다.

두 건 모두 "에러가 나면 바로 보이는 버그"가 아니라 "그럴듯하게 동작하는 것처럼 보이지만 실제로는 매번 실패하는" 유형이어서, 이후 유사한 외부 API 연동에는 실패 상태를 반드시 명시적으로 기록하는 습관을 갖게 됐다.

### 3.4 계획을 바꾼 결정 — 이메일 인증(Resend) 포기

원래 계획은 이메일 OTP로 보호자 인증을 받는 것이었다. 그런데 Resend가 샌드박스 모드에서는 **계정 소유자 본인 이메일 외로는 발송이 안 되는 제약**이 있어서, 팀원들이 각자 이메일로 가입 테스트를 할 수 없었다. 이 문제를 확인한 뒤 OTP 인증 자체를 제거하고, Supabase Auth의 "Confirm email"을 끈 상태에서 이메일+비밀번호로 즉시 가입하는 방식으로 방향을 바꿨다. "계획한 기능을 끝까지 완성하는 것"보다 "제약을 확인하고 팀 전체가 쓸 수 있는 방식으로 빠르게 바꾸는 것"을 선택한 사례다.

### 3.5 하지 않기로 한 것 — Gemini 영상 분석

기획 중 한때 "Gemini로 영상편지를 분석"하자는 안이 나왔는데, 이전에 "AI 안색·표정 진단은 만들지 않는다"고 명시적으로 버린 항목과 충돌할 위험이 있었다. 재논의 끝에 **영상 분석 기능 자체를 만들지 않기로** 최종 결정했다 — 영상편지는 저장(7일 뒤 자동 삭제)과 재생만 제공한다. 만들 수 있는 기능이라도, 이전에 세운 원칙과 충돌하면 만들지 않는다는 판단을 문서(PRD 오픈 이슈)로 남겼다.

## 4. AI 활용 — 맡긴 것과 직접 검증한 것

Claude Code에게 맡긴 일: Supabase 스키마·RLS 정책 설계, Gemini API 연동과 버그 수정, PRD 등 4개 문서의 리브랜딩·개정, UI 버그 수정(글씨 크게 기능 미동작, 연속참여 기록 계산 오류 등), `vercel.json` 배포 설정.

직접 확인·검증한 것: 배포된 화면이 새 탭·모바일에서 실제로 열리는지, 화면과 코드에 개인정보가 노출되지 않는지, Supabase 보안 어드바이저가 지적한 내용이 실제로 고쳐졌는지, Gemini 응답 품질이 실사용 수준인지.

## 6. 남은 한계

- 이메일 인증(Resend)은 샌드박스 제약으로 무인증 가입으로 대체됐다 — 실제 서비스로 전환하려면 정식 이메일 인증을 다시 붙여야 한다.
- 위험도 가중치는 동료심사 문헌 근거로 검증·조정했다(당뇨병 2.4배 → 2.0배). 다만 흡연·이상지질혈증 등 문헌이 함께 다룬 나머지 위험요인은 아직 반영하지 않았고, 독거노인 관련 통계는 여전히 팀이 조사한 2차 자료 수준이다.
- 성별 필드는 DB 스키마에는 추가했지만 화면 노출 여부는 미확정이다.
- 프로덕션 수준의 모니터링(Gemini 호출 실패율 추적 등)은 아직 없다 — 지금까지의 실패는 실사용 중 우연히 발견한 것이다.
