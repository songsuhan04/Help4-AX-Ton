# 데이터 스키마 — Callog(콜록) (팀 헬포)

- 목적: [기능설계서.md](기능설계서.md) §4가 "참고용, 상세 스키마는 별도 문서 필요"로 남겨둔 부분을 구체화
- 범위: 해커톤/코스 단계에 맞는 수준 — 엔티티·필드·관계만 정의. 마이그레이션, 인덱스, 샤딩 등 스케일링 이슈는 다루지 않는다
- 전제: [PRD_통합본.md](PRD_통합본.md)의 **1가족(FamilyAccount) : N어르신(ElderProfile)** 구조 확정을 반영
- **DB**: Supabase(Postgres) 확정. 아래 엔티티는 각각 하나의 테이블로 구현
- **호칭 안내**: 엔티티/필드명은 기존 영문 식별자(FamilyAccount = 보호자 계정, ElderProfile = 어르신 프로필)를 유지한다 — 코드 식별자를 바꾸면 혼란이 커서, 서비스 화면에 보이는 한글 명칭만 "어르신/보호자"로 변경했다.
- **인증 방식 변경**: 전화번호 인증 → **이메일 인증**(Supabase Auth + Resend)으로 전환하며 `FamilyAccount.phone`을 `email`로 변경
- ✅ **적용 상태**: 이 스키마는 실제 Supabase 프로젝트(`songsuhan04's Project`)에 마이그레이션으로 적용 완료됨 (`demo/v1/supabase/migrations/`). RLS 정책·RPC 함수 포함.

## 1. 엔티티 관계 개요

```
FamilyAccount (보호자 계정) 1 ──< N  ElderProfile (어르신 프로필)
ElderProfile               1 ──< N  ElderCondition (지병목록)
ElderProfile               1 ──< N  DailyCheckIn (일일응답기록)
DailyCheckIn               1 ──< 1  VoiceResponse (음성응답, 선택)
ElderProfile               1 ──< N  RiskAssessment (위험도이력)
FamilyAccount               1 ──< N  InviteLink (초대링크)
FamilyAccount / ElderProfile  ──< N  VideoLetter (영상편지, 발신·수신 다형 참조)
ElderProfile               1 ──< N  ElderDevice (기기 연결, 신규)
InviteLink                 1 ──< N  ElderDevice (최초 개봉 시 생성)
```

## 2. 엔티티별 필드

### FamilyAccount (보호자 계정)
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 계정 고유 식별자 (Supabase Auth `auth.users.id`와 동일, FK) |
| email | string | **이메일**(로그인·인증용, 전화번호에서 변경) |
| ~~password_hash~~ | — | 실제 구현에는 이 컬럼이 없음 — 비밀번호는 Supabase Auth(`auth.users`)가 전적으로 관리, `auth.users` insert 시 트리거로 이 테이블 행이 자동 생성됨 |
| auto_login | boolean | 자동 로그인 여부 |
| created_at | datetime | 가입일 |

### ElderProfile (어르신 프로필)
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 어르신 고유 식별자 |
| family_account_id | string (FK → FamilyAccount) | 소속 가족계정 (1가족:N어르신) |
| name | string | 성함 |
| birth_date | date | 생년월일 (화면에는 계산된 나이로 표시) |
| relationship | string | 나와의 관계 (예: 어머니) — 1차 유지 필드 |
| gender | string, nullable | 성별 (`female`/`male`/미입력). 등록·수정 화면의 선택 입력. ⚠️ 위험도 계산에는 쓰지 않음 — 기능설계서 §6-4 참고 |
| nickname | string, nullable | 대상자 목록용 별명 |
| phone | string, nullable | (실제 구현에서 추가) 어르신 전화번호 — 보호자 화면 "전화하기" 버튼의 `tel:` 링크에 사용, 미등록 시 버튼 비활성화 |
| checkin_time | time | 안부 묻는 시각 |
| priority_status | enum(안전, 위험, 심각) | 현재 우선순위 상태 (RiskAssessment 최신값에서 파생) |
| created_at | datetime | 등록일 |

### ElderCondition (지병목록)
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| elder_profile_id | string (FK → ElderProfile) | 대상 어르신 |
| condition_type | enum | 사전 정의 지병 카테고리(고혈압, 당뇨병, 관절염 등) |
| custom_text | string, nullable | 직접 입력한 지병명(사전 정의 목록에 없을 경우) |

### DailyCheckIn (일일응답기록)
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| elder_profile_id | string (FK → ElderProfile) | 대상 어르신 |
| date | date | 응답 날짜 |
| answers | json | ✅ (P0 갱신) 문항별 응답 배열 `[{question, category, choice, severity}]` — category(복약/식사/외출/기분/지병/기타)와 severity(정상/경미/심각)는 `lib/riskScoring.ts`가 위험도를 계산할 때 그대로 사용(자유 텍스트 재해석 없음) |
| questions | json, nullable | (실제 구현에서 추가) 그날 Gemini로 생성된 질문+답변 선택지 세트 캐시(`[{question, options[]}]`) — 같은 날 재조회해도 동일 질문이 유지되도록 최초 생성 시 저장 |
| condition_selfreport | enum | 오늘의 컨디션 선택 |
| skipped | boolean | 오늘 건너뛰기 여부 |

### VoiceResponse (음성응답) — Gemini 기반으로 변경
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| daily_checkin_id | string (FK → DailyCheckIn) | 연결된 일일응답기록 |
| audio_url | string | 원본 음성 파일 경로 (Supabase Storage) |
| transcript | string, nullable | **Gemini 분석 결과 텍스트** (기존 STT 변환 텍스트에서 출처 변경, 필드 의미는 동일) |
| speech_rate | float, nullable | 발화 속도(어절수/분) — Gemini 응답에서 추출 가능한지 검증 필요([기능설계서.md](기능설계서.md) 오픈 이슈) |
| silence_ratio | float, nullable | 침묵 비율 — 위와 동일하게 검증 필요 |
| response_latency_ms | int | 질문 표시~응답 시작까지 반응 지연 (클라이언트에서 측정, Gemini와 무관) |
| analysis_json | json, nullable | (실제 구현에서 추가) Gemini 원본 응답 보존 — speech_rate/silence_ratio를 못 뽑아도 원문은 남긴다 |
| analysis_status | enum(pending, ok, failed, skipped) | (실제 구현에서 추가) 분석 진행 상태 — GEMINI_API_KEY 없으면 skipped로 즉시 넘어감 |
| shared_with_family | boolean | 보호자에게 원본 전송 여부(기본 true) |

### RiskAssessment (위험도이력) — ✅ (P0 갱신) 실제로 채워짐
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| elder_profile_id | string (FK → ElderProfile) | 대상 어르신 |
| date | date | 산정 일자 |
| level | enum(안전, 위험, 심각) | 위험도 등급 — `lib/riskScoring.ts`가 계산해서 씀(서비스 롤로 RLS 우회, 클라이언트 insert 정책 없음) |
| reason | string | 사유 문구(예: "복약을 놓치셨어요(고혈압)") |
| triggered_by | json | 근거가 된 신호(`{score, categories}`) |
| family_action | enum(없음, 전화함, 확인함), nullable | 보호자 대응 상태 |

### VideoLetter (영상편지) — ✅ Gemini 영상 분석을 하지 않기로 확정되어 분석 관련 필드는 두지 않는다
| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| sender_type | enum(family, elder) | 발신자 유형 |
| sender_id | string | 발신자 ID (FamilyAccount 또는 ElderProfile) |
| receiver_type | enum(family, elder) | 수신자 유형 |
| receiver_id | string | 수신자 ID |
| title | string | 한 줄 제목 |
| video_url | string | 영상 파일 경로 (Supabase Storage) |
| sent_at | datetime | 발신 시각 |
| viewed_at | datetime, nullable | 열람 시각 |
| unlock_condition | string | 열람 조건(예: "해당일 안부체크 완료 후") |

✅ (실제 구현에서 추가) 보호자는 자신이 보낸 편지(`sender_type='family' and sender_id=auth.uid()`)를 삭제할 수 있다 — DB 행과 Storage의 영상 파일을 함께 삭제한다. 잘못 촬영한 영상을 되돌릴 방법이 없어 요청된 기능.

⚠️ Gemini 영상 분석 결과를 저장할 필드(예: `analysis_summary`)는 **아직 추가하지 않았다** — 분석 목적(정서적 톤 vs 안색·표정)이 확정되기 전까지 스키마를 섣불리 늘리지 않기 위함이다. 범위가 정해지면 이 테이블에 필드를 추가한다.

|---|---|---|

| family_account_id | string (FK → FamilyAccount) | 발급 주체 |

### ElderDevice (기기 연결) — 신규, 실제 구현 과정에서 추가된 테이블

"초대 링크는 1회용이지만, 한 번 연결되면 계정처럼 계속 유지"(기능설계서.md §2.5)를 실제로 구현하려면 어르신의 익명 세션과 프로필의 지속적 연결을 저장할 곳이 필요해 추가했다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| elder_profile_id | string (FK → ElderProfile) | 대상 어르신 |
| invite_link_id | string (FK → InviteLink), nullable | 최초 연결에 사용된 초대 링크 |
| auth_user_id | string (FK → Supabase `auth.users`) | 어르신의 익명 인증 세션 사용자 ID |
| device_fingerprint | string, nullable | 소프트 기기 마커(localStorage 기반, 하드웨어 지문 아님) |
| created_at | datetime | 최초 연결 시각 |
| last_seen_at | datetime | 마지막 접속 시각 — 무응답 위험 신호의 입력값 |
| revoked_at | datetime, nullable | 재초대 시 즉시 접근 차단을 위한 무효화 표시 |

### PushSubscription (푸시 구독) — 신규, 실제 구현 과정에서 추가된 테이블

보호자 브라우저의 Web Push 구독 정보. 알림을 보내려면 브라우저가 발급한 수신 주소와 암호화 키를 보관해야 한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | string (PK) | 식별자 |
| family_account_id | string (FK → FamilyAccount) | 알림을 받을 보호자 |
| endpoint | string, unique | 브라우저가 주는 푸시 수신 주소. 같은 브라우저가 다시 구독하면 같은 값이 오므로 unique로 두어 중복이 쌓이지 않게 한다 |
| p256dh | string | 브라우저 공개키 |
| auth | string | 브라우저 인증 시크릿 |
| created_at | datetime | 구독 시각 |
| last_sent_at | datetime, nullable | 마지막 발송 시각 |

발송이 404/410으로 실패하면 만료된 구독으로 보고 삭제한다(lib/sendPush.ts).

### DailyPrompt (그날의 질문·주제) — 신규, 실제 구현 과정에서 추가된 테이블

새벽 크론이 그날 쓸 안부 질문과 녹음 주제를 미리 만들어 담아둔다. 예전에는 어르신이 화면을 열 때 Gemini를 호출해서 그날 첫 사용자가 기다려야 했다(근거: 실사용 피드백 — "버퍼링이 걸리더라").

**DailyCheckIn에 합치지 않은 이유**: 보호자 목록이 "그 날 daily_checkin 행이 있으면 오늘 완료"로 판단한다. 미리 행을 만들면 아무도 답하지 않은 날까지 완료로 보인다. 미리 만들어두는 것과 실제로 답한 기록은 성격이 다르므로 따로 둔다.

| 필드 | 타입 | 설명 |
|---|---|---|
| elder_profile_id | string (FK → ElderProfile, PK) | 대상 어르신 |
| date | date (PK) | 한국 날짜 기준 |
| questions | json, nullable | 그날의 안부 문항(DailyCheckIn.questions와 같은 구조) |
| speech_topic | string, nullable | 말하기 안부 주제. 검증에 걸리면 null — 화면이 고정 목록을 쓴다 |
| letter_topic | string, nullable | 어르신 영상편지 주제. 위와 같음 |
| source | string | `gemini` \| `fallback` — AI가 실제로 쓰였는지 확인용 |
| created_at | datetime | 생성 시각 |

**보관 기간**: 14일. 주제 반복을 피하려면 최근 며칠만 알면 되고, 지병·안부 답변에서 뽑아낸 문장을 오래 들고 있을 이유가 없다. 같은 크론이 오래된 행을 함께 지운다.

**AI 문구 검증**: 어르신께 그대로 보이는 문장이므로 생성 결과를 그냥 쓰지 않는다. 의료 조언(처방·복용량·병원 권유), 불안을 키우는 말(위험·악화·쓰러지다), 개인정보 캐묻기, 형식 파괴(줄바꿈·마크업·반말)를 검사하고 걸리면 버린다(lib/dailyTopic.ts).

## 3. 미확정 항목 (오픈 이슈와 연동)

- `ElderProfile.gender`: ✅ 팀 확정 — 선택 입력이므로 nullable 유지(필수화하지 않음). 위험도 가중치에는 미반영(근거 부족, 기능설계서 §6-4)
- `RiskAssessment.triggered_by`의 가중치 수치(고혈압 1.5배, 당뇨 2.0배)는 [기능설계서.md](기능설계서.md) §3 참조. ✅ 두 값은 동료심사 문헌으로 검증됨(`Help4/발표 자료/위험도가중치 근거자료.docx`) — 당뇨는 근거에 맞춰 2.4→2.0으로 조정. 무응답 7시간·외출 3일 임계값은 아직 팀 합의 잠정값
- `VoiceResponse.speech_rate`/`silence_ratio`: 🔶 실제 녹음 3건으로 1차 검증 완료(추출 가능 확인, 표본 부족으로 계속 관찰). 기능설계서 §6-2 참고. 모델명 수정 이전에 `analysis_status='ok'`로 잘못 기록된 빈 행이 있어 기준선 계산 시 제외 필요
- (실제 구현에서 확인됨) Supabase 보안 어드바이저가 `owns_elder`/`is_my_elder`/`handle_new_user` 함수를 "공개적으로 RPC 호출 가능"으로 경고함 — RLS 정책 내부에서 쓰이는 헬퍼라 EXECUTE 권한을 막으면 RLS 자체가 깨지므로 의도적으로 남겨둔 상태. boolean만 반환해 실질적 데이터 유출은 없으나, 스키마를 별도로 분리해 완전히 숨기는 개선은 추후 과제로 남긴다
